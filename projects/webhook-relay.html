Relay: reliable webhook delivery service

2026Solo projectPython · FastAPI · PostgreSQL 16 · Docker · GitHub ActionsSource on GitHub

Problem

Every SaaS product that sends webhooks hits the same problems: receivers go down, time out, rate-limit, or return errors; producers retry and create duplicates; workers crash mid-request. Relay accepts an event once and guarantees each subscribed endpoint eventually receives it, or the delivery lands in a dead-letter queue where it can be inspected and replayed.

Architecture

  • No lost events. The event row and one delivery row per matching endpoint are inserted in one transaction (outbox pattern), so an accepted event can't exist without its deliveries.
  • No duplicate events. UNIQUE(tenant, idempotency_key); a retried POST returns the original event, and the same key with a different body returns 409. Twenty concurrent identical requests produce exactly one event.
  • Safe concurrency. Workers claim with UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED) and set a lease. A crashed worker's rows are reclaimed when its lease expires, and its late write is rejected because attempts no longer matches.
  • Polite retries. Exponential backoff with full jitter, Retry-After honoured, permanent 4xx not retried, dead-lettered after N attempts.
  • Security. Hashed API keys with tenant isolation, HMAC-SHA256 signatures with a replay window, and SSRF blocking of private/metadata addresses at registration and again at send time.

Testing and measurements

44 pytest tests run against real PostgreSQL in CI: 5xx, timeouts, connection errors, 404/410 to dead-letter, max attempts, Retry-After, replay, crashed worker plus stale write, four concurrent workers (60 events, zero double deliveries) and concurrent duplicate POSTs. A real-process demo (API + worker + receiver that fails twice) shows 503 → 503 → 200 on attempt 3. A benchmark of the claim → deliver → record loop measured ~800 deliveries/s with one worker and ~1,040/s with four on a 2-CPU VM. The receiver there is an in-memory mock, so this is Relay's own database overhead, not network delivery speed.

Limitations and next steps

  • No per-endpoint circuit breaker or rate limit yet.
  • DNS-rebinding window between the SSRF check and the connection; fix by pinning the resolved IP or using an egress proxy.
  • No retention job for old attempts; add partitioning or pruning.
  • Prometheus metrics endpoint.
